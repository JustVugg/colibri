## 1. `vk_dmoe.h`'s exact contract

### Functions (all `static`, header-only, included after `vk_chain.h`/`vk_tier.h`)

| fn | line | what it does |
|---|---|---|
| `vkc_dmoe_prepare(d, lo, L, E, K, D, I, rows)` | 511 | once per step/kind. Hard gates: `COLI_VK_CHAIN_MOE != 0` (125), `!off`, `rows > VKC_DMOE_ROWS` only if `d->big`, `L>=1`, `vkc_device_now()==0` (primary device only), `vkt_ready()`, `vkc_moe_ready()`, `vkc_route_ready()`, `1<=K<=VKC_ROUTE_KMAX(32)`, `K<=E<=VKC_ROUTE_EMAX(1024)`. | `vkc_dmoe_layer(d, layer, n, lg, bias, x, rt, mp)` | 600 | route (`vkc_route`) + experts (`vkc_moe` for `n<=8`, `vkc_moe_rows` for big steps, or the hybrid 3-frame CPU/device split) → `d->y`. ### What a participating engine must provide
* `VkcDmoe dm` in its chain struct, plus per-layer `vkc_dmoe_on` + `dm.y` in place of the host's routed buffer (see `olmoe_chain.h:610` and the `prev_dev ? ch->dm.y : ch->routed` combine at `olmoe_chain.h:606-607, 649-650`).
* **A `lg` buffer on the device with the router logits** (`n` rows × E) and the router's parameters in a `VkcRoute` (`vk_chain.h:404-421`): `kind` 0 softmax / 1 sigmoid / 2 sqrt(softplus), `has_bias` 0/1/2, `n_group/topk_group`, `norm` 1/2, `temp`, `scale`, `norm_eps`. And an optional bias `VkcBuf`.
* A `VkcMoe` (`vk_chain.h:435-445`): `D`, `I`, `act` (0 SwiGLU, 1 SiTU), `limit`, `a`, `b`, `blocks=0` for colibri formats (1 = GGUF block decoders), `E`.
* **Expert table format**: nothing of its own — the tier's `COLI_VK_XB_ENTRY`=32-word entries (`backend_vulkan.h:301-305`): `[0..1]` gate w BDA, `[2..3]` gate scales, `[4..7]` up, `[8..11]` down, `[12]` gate/up fmt, `[13]` rowWords, `[14]` gs, `[15..17]` down's, `[18]` 1 = resident (0 = skipped). Read via `vkt_dev_table(layer, ent)` (`vk_tier.c:2940`), which returns **the count of device-resident experts**; `d->on[i] = (n == E)` (`vk_dmoe.h:275`) — **all-or-nothing per layer**.
* **Bookkeeping after the frame**: `vkt_dev_count(layer, n, K, vkc_dmoe_ids(...))` (heat/promotions/streaming), plus whatever its own router counts (`rt_count`, `ehit_mark`) — `olmoe_chain.h:531-537`.
* **Epoch rules** (`vk_dmoe.h:29-36`): a layer the host steps through runs the tier, which may evict/free/upload experts; a frame that read the table earlier would read freed memory. Hence `vkc_dmoe_upload` at every frame start (first frame and after any host layer), `vkt_epoch()` compare in `vkc_dmoe_on`, and `vkt_settle()` inside upload. Engines call upload after the host's step (`olmoe_chain.h:583, 646`).
* `d->big = 1` opts into chunk rows (`olmoe_chain.h:175`); otherwise `rows > 8` makes `prepare` fail by design.

### Callers today
`vk_dmoe.h` is included by exactly **`olmoe_chain.h:57`, `qwen36_chain.h:77`, `qwen38_chain.h:59`**. **Not** glm53/kimi/inkling/mimo/deepseek_v41/deepseek_v4 (`deepseek_v4_chain.h:90-91` includes only `vk_chain.h`, `vk_kv_split.h`). qwen38 also runs a 1-layer dmoe for its MTP head (`qwen38_chain.h:1392-1444`).

per chunk of rows:

## 2. The fmt-7 gap, precisely

DSV4 expert formats: **fmt 7 (MXFP4), gs 32, both gate/up and down** (`bench/up2276/merge-all2-r1.log:18`). E=256, topk=6, D=4096 (`deepseek_v4.c:12467`).

### Where fmt 7 is rejected / handled
* `our_fmt(f)` = `f==1||f==2||f==4` — **`c/vk_chain.c:2598`** (the task's `:2598` anchor confirmed).
* `vkc_moe_rows_ready(gfmt,dfmt)` — **`c/vk_chain.c:2665-2669`**: `bd = gfmt>=100 && dfmt>=100 && block table`, `q = our_fmt(gfmt) && our_fmt(dfmt)`. fmt 7 → neither → **0**. This is the single hard gate: `vkc_moe_rows` re-tests it (`:2678`) and returns 0.
* `rows_pipe1(v,f,coop)` — **`:2599-2601`** has no pipeline for 7; `rows_pipe/rows_coop` (`:2604-2612`) likewise.
* `vkc_moe` (the ≤8-row path) does **not** reject fmt 7: `moe_fi(7)==0` (`:2201`) only means "no format-specialised pipeline", so it uses the every-format `KC.moe[0][b]` made with `fmt=0` (`:2218-2243`) and `chain_moe.comp` decodes fmt 7 at `chain_moe.comp:184` (`else if (fmt == 7) block_7(...)`) and `:319` (`else if (fmt == 4 || fmt == 7)`, scales `Sc.v[sb + i0/gs]`). `moe_gv_pipe(7,…)` returns NULL (`:2246-2249`) so the fast `chain_moe_gv` layout is skipped, not broken.
* In `vkc_dmoe.h`: `d->rows_off[i] = on[i] && !vkc_moe_rows_ready(fmt12, fmt15)` (`:533`), and `prepare` returns 0 for the whole big step if **no** layer qualifies (`:536`). So today a DSV4 prompt chunk can never enter the chain MoE; the ≤8-row (decode) path can.

### What the item/amap/etab encoding needs (route (a) is already 95 % built)
`chain_moe_rows.comp` mode 1 (`:83-133`) writes one 16-word `etab` per expert per pass: `[0..7]` = gate(+up) w/scales BDAs, `[8]` = the expert's row count, `[9]` = its first packed row, `[10]` = fmt, `[11]` = rowWords, `[12]` = gs, `[14..15]` = block-decoder table; and `items[] = (expert, first row, output block, 1)` with `nob1=(I+31)/32`, `nob0=(D+63)/64` (TM=32 rows a tile). `aux[0]=tiles*nob1`, `aux[4]=tiles*nob0` drive the two indirect dispatches.

`qmatmul_grp_mx.comp` reads **exactly that**: `etab[eb+0..1]/[+2..3]` (g w, g scales), `[+4..7]` (up), `[+8]`=S, `[+9]`=xoff, `[+11]`=rowWords, `[+12]`=gs, x through `amap[xr]/kgat`, `y[yr]` with `yr=amap[...]` (`:60-70, 100-152`); `BO=32` for GATE_UP and `64` for down — the same output-block geometry the planner already emits. Bindings (0..4) and the 5-binding layout are identical to `qmatmul_grp_bd.comp`. Only the push constants differ: mx wants `{I,O,limit,ibase,kgat,rpw,act,a,b}` = 36 B, bd wants `{I,O,limit,ibase,kgat,rpw}` = 24 B (`qmatmul_grp_mx.comp:41` vs `qmatmul_grp_bd.comp:31`; `vk_chain.c:2699, 2705` build the 24 B struct). Shared memory: mx GATE_UP = (2×32 + 32)·17 vec4 = 26,112 B < `ROWS_GRP_SHARED` 35,648 (`vk_chain.c:2645`) → fits the existing `rows_make` bar. `vk_chain`'s pipeline layout allows 128 B of push constants (`vk_chain.c:517`).

## 3. The three candidate routes

### (a) Extend `vkc_moe_rows` to fmt 7 via the mx mode-4 shader — **RECOMMENDED**
Files/lines to touch, all in `c/vk_chain.c` (+ one test row):
1. `:129-133` KC struct: `VkShaderModule mod_mx[2]; VkPipeline mx[2]; uint8_t mx_tried[2];`
2. `:2586-2596` beside `grpq_pipe`: `mx_pipe(v)` → `load_module("qmatmul_grp_mx.spv"/"…_gate_up_mx.spv")`, `make_pipe(mod,NULL)`, no specialization (no coop variant).
3. `:2598` `our_fmt` unchanged; add `mx_fmt(f) = (f == 7)`; `rows_pipe1` → `f==7 ? mx_pipe(v) : …`; `rows_coop` → 0 for 7.
4. `:2667` `vkc_moe_rows_ready`: `q = (our_fmt(g)&&our_fmt(d)) || (g==7 && d==7)`, plus `rows_make()` + `mx_pipe(0) && mx_pipe(1)`.
5. `:2699-2706` two 36-byte push-constant structs for the 7 case (`act=0`, `a=b=0`, `limit`), selected on `p->gfmt==7`.
6. `:3373-3381` destroy the modules/pipelines; optionally prewarm in `vkc_prewarm` (`:2382-2405` the rows block already loops over `ex_gu/ex_dn`).
7. `c/tests/test_vk_chain.c:3366-3372, 4466-4469`: `test_moe_rows_q(7, 32, 40, 4, 12, 512, 256)`; make the byte/group sizes use `fmt==7` like `fmt==4` (`rg = D/2`, `ng = D/gs`).
**LOC ~60-90 (chain) + 2 (test). Numerics class**: float arithmetic, one dispatch per item, k accumulate ascending → not bit-identical to `vkc_moe`/the CPU, same class as the tier's mode 4 (worst rel. err 3.8e-07, commit `0e79f870`); **it breaks the "a row's bits don't depend on the chunk" invariant** the DSV4 chain documents (`deepseek_v4_chain.h:1189-1201`) — prompts only, so gate it behind an opt-in like `COLI_VK_CHAIN_GEMM_ROWS`. No shader work, no Makefile work (`c/Makefile:764, 955-960` already build the two .spv).

### (b) A new `vkc_dmoe_*` arm / kernel for fmt 7
Only worth it if (a)'s per-item scheduling is too slow: a fmt-7 sibling of `chain_moe_gv.comp` (per-token 8-nibble decode, "lanes a row") for the S≤8 path, or a fused gate/up/down chain MoE. Files: new `c/shaders/chain_moe_mx*.comp` + `c/vk_chain.c` plumbing (mirroring `moe_gv_pipe` `:2246-2264`) + `vkc_dmoe_layer`'s selection. **LOC 250-450 (+ shader tuning).** Numerics: its own class again (a new accumulation order), and it forfeits the "same bits as chain_moe" argument. Only justified if measurement (see §5) shows `chain_moe`'s generic fmt-7 path is the bottleneck (it uses `rpw=64/spl=8` for our formats, i.e. `i4`-shaped workgroups, while fmt 7 wants 8 weights/word like fmt 4 — plausible 1.3-2× miss).

### (c) Re-encode fmt 7 to an accepted format at load
Reject. (i) fmt 1 (int8) or fmt 2/4 (int4) means a **requantisation** (e2m1 codes are not representable by the linear i4 LUT), so the numerics change (a different weight quantisation, not a re-layout). (ii) Bytes: fmt 2/4 ≈ same size as fmt 7, so no VRAM/RAM win, but fmt 1 doubles the 167 GB expert set. (iii) It must be done once for 10,543 experts × 15.0 MiB = **167 GB** → a disk rewrite at import (a converter tool), or an impossible in-RAM pass. (iv) It would have to happen *inside* the tier's expert tensors or the tier's `ColiVkTensor` fmt would no longer match the file. Not a slice; only a fallback if (a) is falsified.

### How each composes with the tier (resident experts + streaming + warm start)
* **Chain MoE replaces the tier's *batch*, not the tier.** For a qualifying layer the experts' GEMVs/GEMMs are issued by the chain's recorders inside its own frame; there is no `coli_v4_moe_routed` call, no `v4_apply_expert_batch`/`xb_*` dispatch, no host round trip. Residency, streaming, promotions, heat and the LRU stay the tier's (`vkt_dev_table` in, `vkt_dev_count` out).
* **Streaming fights the gate.** `on[i]` needs *all* E experts of a layer resident (`vk_dmoe.h:275`). Streaming (`vkt_stream_prefetch`, `deepseek_v4_chain.h:1300`; tier `stream:` line) uploads *cold* experts into slots and evicts them after the step; every such epoch change flips `on[]`/`rows_off[]` off and forces a whole-table re-read (`vkc_dmoe_read:263-296`). So the two mechanisms interleave badly: a forward that streams loses its chain-MoE layers. Order of work matters: chain layers first with no streaming; the streaming path stays for the rest.
* **Residency arithmetic is the wall (this is the decisive feasibility fact).** An expert is **15.0 MiB** (`bench/up2276/merge-all2-r1.log:18` "337 experts of 15.0 MiB"); a layer is 256 × 15.0 MiB ≈ **3.75 GiB**. The measured tier budgets are 7.79 GiB with **465 / 465** or **331 / 337** experts resident — i.e. 1.2–1.3 layers' worth, spread over 43 layers by heat. So at these budgets `on[i]` is essentially never true for DSV4, and L2 gives **0 layers**. Raising `COLI_VK_TIER_GB` (`vk_tier.c:2628`) to ≥ 3.9 GiB **of pinned residency per layer** is a precondition of the whole slice; the tier has no "pin this layer" lever today (**OPEN** — the warm start plans from the `.coli_usage` heat file, `vk_tier.c:925-960`; the cheapest test lever is a temporary `COLI_VK_TIER_PIN_LAYER=n` that queues layer n's 256 slots in `vkt_plan`, ~8 lines, or a hand-edited usage file).
* Warm start/promote/stream are otherwise untouched; `vkt_settle` in `vkc_dmoe_upload` (`:564`) is what makes them visible to the chain.

## 4. The decode side: `VKC_DMOE_ROWS`=8 vs S=1

* `VKC_DMOE_ROWS 8` (`vk_dmoe.h:52`) is a **ceiling on the per-pair path**, not a minimum. `vkc_dmoe_prepare` accepts any `rows`; `vkc_dmoe_layer` uses `vkc_moe` when `n <= 8` (`vk_dmoe.h:636-640`) and `vkc_moe_rows` only when `n > 8` (`:627-635`). `vkc_moe` accepts `S >= 1` (`vk_chain.c:2478`) and `chain_moe.comp` is written per (row, slot) pair ⇒ **S=1 decode is served**, and it is the *only* path DSV4 can use today (fmt 7 passes `chain_moe.comp`, fails `vkc_moe_rows_ready`).
* Therefore the DSV4 decode arm needs **no fmt-7 kernel at all**; the fmt-7 gap only bites prompt chunks (`COLI_VK_CHAIN=2` / `COLI_VK_CHAIN_ROWS`, `deepseek_v4_chain.h:75`).
* What participating engines do at S=1: nothing special — they simply stay on the per-pair path; `olmoe/qwen36/qwen38` all call the same `vkc_dmoe_layer` and let it branch on `n`. Their only S-dependence is buffer sizing (`r = rows > VKC_DMOE_ROWS ? rows : VKC_DMOE_ROWS`, `olmoe_chain.h:517-519`) and `d->big` (`olmoe_chain.h:175`).

## 6. Feasibility verdict (do not skip)

The premise "move the 140 s of host-side routed-expert *compute* onto the device" is **partly a misattribution**. Measured in this tree (RX 6900 XT 16 GiB, DSV4-Flash, 2515-token prompt + 64 generated tokens, `bench/up2276/merge-all2-r1.log:31,41,42`):

* decode 64 tokens in 309.4 s; `140.9 s` "of routed experts on the host" (`:41`); only `15.0 s` waiting for the device.
* the tier's own split for the whole run: `device 28.1 s, CPU share 69.9 s, waited 24.0 s`, `stream: 189.76 GiB`, `disk loads 19556`, `CPU RAM hits 9138`, expert bytes touched 261 GB (`:31`).
* So of the 140.9 s a large share is **waiting for expert bytes** (disk + PCIe + the tier's CPU pool), not arithmetic a device GEMV would replace. `decode-prof.log:33` shows the same shape harder (8 tokens/240 s, `CPU share 96460 ms` vs `device 5795 ms`).
* The part chain-MoE genuinely removes: per-layer host round trips (the `vkc_finish()` wait per layer, `deepseek_v4_chain.h:1300`, and `15.0 s`/64 tokens of device wait = 5 % of wall), the host gate matvec (already on device via `coli_v4_vk_matmul`, `deepseek_v4.c:10923`, for S=1 too), the per-token MoE C orchestration and two D-float copies per layer.
* **Ceiling with zero residency work ≈ 3-8 % of decode wall**; the `+25-60 s` in `P-optionB…:498` assumes experts are on the device, which the residency arithmetic above forbids (1.2 layers fit, a layer needs 3.75 GiB).
* ⇒ L2's value is (i) upstream alignment, (ii) a *prerequisite vehicle* for the residency/hot-set work (L3), not a standalone 140 s win. Say this in the PR; do not promise the 140 s.

## ARCHITECTURE (one paragraph)
The tier (`vk_tier.c`) owns expert bytes and residency and publishes a 32-word per-expert device-address table (`vkt_dev_table`) plus an epoch/changes log. `vk_dmoe.h` is the chain-side consumer: it copies that table into a device buffer, and for each layer the tier holds *entirely*, records `vkc_route` (chain_route.comp) followed by `vkc_moe` (chain_moe.comp, per (row,slot) pair — fmt 7 capable) or `vkc_moe_rows` (chain_moe_rows.comp plans items/etab/amap, then `qmatmul_grp_{bd,q}_*.comp` runs them — fmt 1/2/4 and GGUF blocks only), all inside the engine's own frame, then feeds the ids back to `vkt_dev_count`. DSV4 today never enters this path: it submits per layer, waits, runs `coli_v4_moe_routed` on the host (which re-does the router in bf16 and drives the *tier's* batch through `backend_vulkan.c`'s `xb_grp_*`, the only place fmt 7 has a grouped GEMM — mode 4, `qmatmul_grp_mx.comp`, brand new in `0e79f870`).

## OPENs
* `config->num_hash_layers` for DSV4-Flash — not in any in-tree log; hash layers can never use `vkc_route` (needs a token→expert table arm in `vkc_route` or a per-layer skip).
* `config->moe_intermediate_size` (I). From 15.0 MiB/expert at fmt 7 gs 32 I ≈ 2304; the mx shader needs `I%64==0` ✓, but confirm.
* No pin-a-layer lever exists in the tier (**blocking** for S1's residency precondition, `vk_tier.c:905-948`). `COLI_VK_TIER_PIN_LAYER` is proposed, not implemented.
* Mismatch in the task's anchors: no in-tree log has exactly `140347.7 ms / 190.97 GiB / slots256`; closest verified are `merge-all2-r1.log` (140 877.7 ms, 189.76 GiB, slots 192) and `merge-mx-gr4-r1.log:40` (238 286.7 ms). Numbers above use the verified logs.
* Sum order differs from the CPU: the CPU accumulates per position in **ascending expert id** (`deepseek_v4.c:6233-6241`), `chain_moe.comp` sums in **rank order** (`vk_chain.h:432`, `chain_moe_rows.comp:74-80`). Not bit-identical; the bf16 round after the join absorbs most of it — must be asserted by the greedy/oracle gate, not assumed.
* Whether fmt 7 through the *generic* `chain_moe.comp` pipeline (rpw=64/spl=8, the `i4` shape) is fast enough at S=1/K=6 is unmeasured — it decides whether route (b) is ever needed.
