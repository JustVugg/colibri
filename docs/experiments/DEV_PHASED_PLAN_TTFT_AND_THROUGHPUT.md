## 1. Objective

Move Colibri from being primarily decode-throughput optimised to being **interactive-agent optimised**.

For Hermes, Brewer and Copilot, the first response matters. A model that generates quickly after a long silent prefill can still feel slow.

The programme has four objectives:

1. Reduce time-to-first-token (TTFT), especially for long prompts.
2. Avoid reprocessing conversation history when existing model state can be reused safely.
3. Use available RAM deliberately without causing memory pressure or swap.
4. Preserve decode throughput while evaluating model and quantisation alternatives.

Initial prompt sizes: **1K, 4K, 12K, 32K and 66K tokens**. These are workload points, not a claim that every model/configuration supports 66K. Verify each model's effective context limit first.

## 2. Baseline and known evidence

The following are historical observations in `docs/experiments/DEV_PLAN_10TO15_TOKS.md`, not fresh measurements from this plan.

### Qwen3.6 35B-A3B IQ2_XXS

- 40 layers, 256 routed experts, top-8.
- C11 fused ARM IQ2/IQ3 kernels reduced recorded MoE block time from about 42.7 ms to 28.4 ms.
- Recorded plain decode after C11: approximately 14.43–14.59 tok/s.
- Recorded MTP-on decode: approximately 12.99–13.59 tok/s, with D1 the best tested draft depth.
- MTP acceptance was useful, but draft-head cost became a net loss after the main model's verify path became faster.
- Current practical baseline: MTP off/unset unless a new end-to-end test proves otherwise.

### Qwen3.6 27B dense IQ2_XXS

- Dense model, not MoE.
- Branch log records a 9.56 GB model and a working native GGUF MTP head.
- CPU and Metal results are substantially below the 35B MoE decode result.
- Still valuable as a controlled workload for dense prefill, Metal GEMV and MTP-head experiments.

### Existing mechanisms to build on

- `kv_prefix.h`: records token IDs actually fed into the engine and permits exact-prefix reuse where engine state is valid.
- `c/tools/benchmark_http_serving.py`: streaming benchmark with client-observed first-output distributions (p50/p95/p99), request duration and optional arrival-rate/SLO data.
- `prompt_break.h` and Qwen36 prompt control: safe prompt-stop boundaries.
- C3 mmap expert access: file-backed expert weights with OS read-ahead/discard hints.
- Latest branch commit adds opt-in `Q36_HYBRID_GB`: selected hot experts can be promoted to owned RAM copies while cold experts remain mmap-backed. This is new and has no performance conclusion yet.

**Measurement distinction:** client-observed first-output latency is not a complete diagnosis of engine TTFT. It includes some combination of queueing, HTTP, tokenisation, prompt preparation, prefill, logits, sampling and stream delivery. Gateway timings and Qwen3.6 tokenization, prefix/snapshot, prefill-operation, first-sample and first-text-emission measurements are implemented. The C12 workload matrix and real-model baseline collection remain outstanding.

## 3. Programme principles

1. Measure before changing kernels.
2. Optimise real agent sessions, not only isolated prompts.
3. Separate cold, warm and prefix-reuse behaviour.
4. Preserve correctness. KV reuse and recurrent-state changes require explicit validation.
5. Treat memory as a budget, not a guaranteed physical reservation. macOS may compress memory or reclaim file-backed pages.
6. Keep model comparisons fair: same prompt tokens, context settings, sampling, output limit, warmup and concurrency.
7. Use repeated runs and report distributions.
8. Do not regress established decode performance for a synthetic prompt win without an explicit trade-off decision.

### C13 — Conversation prefix reuse validation and optimisation

**Priority:** P0 after C12 · **Status:** Telemetry implemented; real-model validation passed for disk-restore, live-reuse and divergent cases (2026-11-11), the three-fix phase-3 sequence, and the phase-4 truncation/reset/4K-repeat/append cases (2026-11-12). Code preserves informative live-state miss labels, supports exact-repeat disk restore using saved logits, lowers the default snapshot threshold to 256 tokens, and prunes by mtime with restore-touch LRU under both a file-count cap and a total-bytes budget (`COLI_PROMPT_CACHE_GB`, default 8). The macOS build and targeted fixture-backed runtime tests pass (16 passed, 1 skipped); a MinGW-w64 cross-build from macOS also produced a verified PE32+ `qwen36.exe`. This verifies compilation/linking, not execution on Windows. Multiplexed serving (`KV_SLOTS=2`) and the byte-budget retention are validated on the live stack (2026-11-12, phase 5). Remaining cases include the native Windows runtime test.

**Goal:** Avoid processing prompt tokens whose model state is already available and valid.

1. Audit `kv_prefix.h` integration in Qwen36 serving and other relevant engines.
2. Measure exact-prefix hit rate, reused token count/percentage, time saved, and miss reasons.
3. Validate that prefix records always describe tokens actually fed into the model.
4. Preserve the conservative recurrent-state rule: do not resume from an arbitrary partial common prefix unless the exact recurrent state for that position can be restored.

6. Consider snapshots/checkpoints only if measurements show exact-prefix reuse is insufficient and state cost is justified.

### C14 — Budgeted hybrid RAM residency

**Priority:** P1 · **Status:** Phase 0 verdict 2026-11-13: prefill MoE >95% matmul compute, reads <1% of bus — residency has no steady-state TTFT headroom; benchmark re-aimed at the memory-pressure decode arm · **Scoping update 2026-11-13 (C15 phase 0 fallout): expectations re-anchored below****Goal:** Use user-approved memory headroom to keep frequently used routed experts in owned RAM copies while retaining mmap-backed access for cold experts.

The latest commit introduces `Q36_HYBRID_GB`. It estimates a per-layer hot-expert count from a GB budget, collects route frequency and promotes selected mmap-backed experts to owned copies. Cold experts remain mapped.

This is promising, but code landing is not proof of a speedup.

Test budgets **0, 1, 2, 3 and 5 GB** using the same prompt/session workload. Record:

- Actual resident memory and memory footprint.
- Compressed memory, swap growth and memory pressure.
- Expert hit/miss and promotion counts.
- Expert read/promotion time.
- Decode tok/s, prefill tok/s and TTFT.
- Stability over a sustained multi-turn session.

Keep MTP-head memory accounting separate from main-model expert residency. The MTP expert slab previously measured about 278 MB in the recorded 35B configuration; this does not justify an arbitrary fixed reserve without measuring all associated weights and buffers.

Review promotion/eviction for concurrency safety, pinned-slot limits, allocation failure and fallback behaviour. Confirm the budget calculation cannot silently exceed its requested allowance.

**Design direction:** expose a clear user-configurable upper budget, not a hard RAM lock; preserve OS/application headroom; promote hot experts only when measured reuse justifies it; observe MTP weights/buffers separately; avoid aggressive prefetch that causes cache pollution.

**Acceptance:** retain a budget only if repeated measurements improve a target workload without unacceptable TTFT, decode, memory-pressure or swap regressions. 5 GB is a test point, not an assumed default.

**Scoping (2026-11-13, from the C15 phase-0 shares + code reading): residency cannot be the prefill-TTFT lever; its value is decode robustness under memory pressure.**

- Expert geometry (config): 256 experts, top-k 8, expert width D=2048, intermediate I=512 → 3·D·I ≈ 3.15 M params/expert ≈ 0.81 MB/expert at IQ2_XXS (~2.06 bpw) ≈ **207 MB/layer, ~8.3 GB of routed weights** — matching the +8.7 GB first-prefill RSS growth the memory run recorded (lazy expert paging).
- The path on this host (CPU GGUF serve → `use_gq` → `moe_gq_run`, qwen36.c ~6244): counting-sort the S·K (token, expert) pairs by expert, then per *activated* expert one `gq_matmul2_act` (gate+up) and one `gq_matmul` (down), weights read **directly from the page-cache-backed mmap** (`gq_slot_W` — "C3: point, don't copy"; no per-use copies to skip). The inner kernel on Apple silicon is the fused NEON `gq_dot_arm_iq2_xxs` (one weight row's registers reused across all its activation rows); the AVX2 batched prefill kernels (`GQ_R16_ON`/tile16/f8, "unpack 16 file rows once") are **x86-only** and do not apply here.
- Compute arithmetic: a 12K prefill issues ≈ 40 layers × 8 experts × 3 matmuls × 2·D·I ≈ **2.0 GFLOP/token ≈ 24.9 TFLOP total**; at the measured 320.5 s MoE time that is ~78 GFLOPS over 6 threads (~13 GFLOPS/thread) — the profile of a scalar-ish NEON int8-dot dequant loop, i.e. **compute-bound**.
- Data movement is bounded *by the measurements themselves*: a full 8.3 GB expert stream at this host's 120 GB/s (M4 base) is ≥ 69 s — more than the *entire* 4K MoE time (102 s) once compute is added, which is impossible; so router activation skew keeps the per-prefill stream well under the full weight size, and the stream is page-cache-served in any case (the memory run showed the pages stay resident between colds; later colds added only +212/+268 MB RSS). Flat ms/token across sizes (23.6 → 24.9 → 26.0 at 1K/4K/12K) says the same: a stream-once term would *fall* per token as S grows.
- **Consequence 1 — prefill TTFT:** `Q36_HYBRID_GB` cannot materially improve long-prompt TTFT. The binding prefill-MoE cost is the fused-dot compute, not where the weights sit. The real prefill-MoE levers are kernel work: profile the `gq_dot_arm_iq2_xxs` inner loop, or evaluate the C10b int8-expert path (`q36_exp_i8_on`, `matmul_q_idot`) as an accuracy-gated A/B — different numerics, needs its own correctness story, not bit-exact.
- **Consequence 2 — decode:** one decode token streams 8 experts × 3.15 M params × 2.06 bpw × 40 layers ≈ **256 MB**; at 8.6 tok/s (12K ctx) that is ≈ 2.2 GB/s — an order of magnitude under M4 bandwidth. Decode expert cost is per-expert n=1 GEMV latency/compute, not residency; consistent with prompt-lookup's null decode result (15.5 vs 16.3 tok/s).
- **Where residency CAN matter:** insulating decode from page-cache eviction on this 16 GB host under real co-tenant memory pressure (the brewer contamination incident is the existence proof that pressure events happen), and multi-turn stability. The benchmark plan above stays, but an idle-host arm will likely measure ~0 delta — the informative arm is **under memory pressure**, and its metric is decode tok/s stability, not TTFT.
- **C14 phase 0 result (2026-11-13, `phaseC14_p0_moeprof_results.jsonl`, `phaseC14_repeat_test.jsonl`, instrumentation commit `dea86efd`; NOTE: the raw JSONL rows carry the hold/mm/act buckets in **ms** — a unit bug fixed post-run by `/1000` in the clk deltas, commit pending):** the profiler splits prefill MoE per request. At 12K: matmul **322.6 s = 92% of moe_total 349.7 s**; silu activation 4.3 s; shared 13.0 s and router 8.0 s are their own accumulators; **expert hold 0.65 s (0.2%)**; weight bytes touched 9.19 GB of a ~9.8 GB routed universe (240 of 256 experts activated per layer average; 217 at 1K, 240 at 4K/12K). Required read bandwidth if every touched byte crossed the bus: 0.37 / 0.09 / 0.03 GB/s at 1K/4K/12K — **<1% of the ~120 GB/s bus at every size** (the scoping's earlier "~47 GB/s"-class worry, and a transient 374 GB/s anomaly during analysis, were both arithmetic slips of ×1000 — the measurements leave no stream term to find). Routed compute rate is flat across sizes: 77–93 GFLOPS over 6 threads (13–15.5/thread), slightly declining at n≈455 rows/expert (12K) from L2 pressure on the X/G/U/Y scratch.
- **Repeat test (same 106-token prompt twice in one process, cache off, identical activation sets — 5.29 GB touched, 33,920 pairs both passes):** mm 4.34 → 2.35 s (−46%). The ~2.0 s delta is the **cold-page materialization cost** (soft faults + page-cache/SSD fill at ~2.6 GB/s effective for the touched expert universe), paid by the FIRST prefill of a process whose file pages are not resident; steady state on this host is warm (the memory run's later colds added only +212/+268 MB RSS). Two single-thread microbenchmarks bracket the machine: cold mmap read ~0.6 GB/s (disk-bound under the engine's ~10 GB RSS pressure), warm streaming ~16 GB/s single-thread (6-thread aggregate ≥ several× that).
- **C14 verdict, measured:** prefill MoE is **>95% matmul compute**; hold + silu + data movement together are <8% (mostly shared/router, which residency cannot touch). `Q36_HYBRID_GB` has **no TTFT headroom in steady state**. Its residual value is exactly the pressure story: insulating decode from page-cache eviction (the repeat test quantifies what a cold touch costs: ~SSD-rate, i.e. minutes if a large expert universe is evicted mid-session) and multi-turn stability. The benchmark plan stays with the pressure arm as the informative one; idle-host arms should be expected to measure ~0. The TTFT lever inside MoE remains the kernel itself: the ARM fused `gq_dot_arm_iq2_xxs` inner loop (profile it) or the C10b int8-expert path as an accuracy-gated A/B.

- **Pressure-arm benchmark spec (2026-11-14, set built, pending run):** four arms, same committed binary, interleaved in a fixed order over two rounds (drift rule): `idle0` (no hog, `Q36_HYBRID_GB` unset), `idle2` (no hog, `Q36_HYBRID_GB=2`), `press0` (hog, unset), `press2` (hog, `=2`). Pressure = the co-tenant hog `c14_hog.c` (default 5 GB anonymous, touched and re-touched every 15 s — genuine resident pressure against the engine's ~10 GB RSS on the 16 GB host), started only after the arm's server is up. Workload: `c14_pressure.py` — ONE 4-turn agent-session conversation per run, actual engine outputs replayed as the next turn's assistant messages, per-turn prompts ≈ 2.5K then small follow-ups (cache ON — realistic multi-turn; within-arm reuse expected live), 128 decode tokens per turn for a rate window. **Metric of interest: per-turn `decode_tokens_per_sec` stability;** the gates are (a) idle arms ~0 delta between hybrid 0 and 2, (b) whether decode degrades under the hog with hybrid 0 and whether hybrid 2 insulates it — paired within-round deltas only. TTFT under pressure is expected to absorb re-fault costs and is recorded as secondary. `vm_stat`/swap snapshots bracket every run (`phaseC14_pressure_vmstat.log`). Launcher `c14_pressure_launch.sh`, verdict `c14_pressure_summary.py`, ~1 h end to end. Expectation from the repeat test: if a large slice of the resident expert universe is evicted mid-decode, recovery runs at SSD rate (~2.6 GB/s materialization measured) — decode should visibly sag in press0; the question press2 answers is whether the 2 GB hot copy prevents that.

- **Pressure-arm verdict — NULL result, measured (2026-11-14, `phaseC14_pressure_{arm}_r{1,2}.jsonl`, verdict `phaseC14_pressure_verdict.txt`, ~5 GB hog, swap used 483 MB during press arms so real pressure existed).** Outputs sha-identical across every arm and turn (t1 `456ecc343f37` ×8, t2–t4 `2d2dd447f7a6` ×24) — data placement changes no numerics, as expected. **The decisive finding is the noise floor: per-turn decode rate on this host varies ±40–95% turn-to-turn at identical config** (2.46–7.87 tok/s across arms including idle-vs-idle pairs), so no arm effect is measurable: hybrid 2 vs 0 means −4.2% (idle) / +12.2% (press) — both inside the scatter, and **pressure vs idle (hybrid 0) mean +18.3%, i.e. the 5 GB hog did not degrade decode at all**. The cleanest comparison — t1 (fresh state, same 1,948-token prompt every arm) — bands tightly at 7.47–7.87 tok/s across all four arms (±5%), confirming: no pressure effect, no hybrid effect. TTFT under pressure rose only ~9% (51.6–53.7 s vs 44.1–53.5 s idle) — re-fault costs absorbed, as predicted. **Consequence: `Q36_HYBRID_GB` stays default-off; at this pressure level it has no measured value and no measured cost.** Caveats: (a) the 5 GB hog against the engine's ~10 GB RSS produced swap use but may not have evicted the hot expert universe — a stronger hog (7–8 GB on the 16 GB host) is the escalation if a forced-eviction arm is ever wanted; (b) the ±40% turn-to-turn decode scatter is itself a finding: single-turn decode-rate comparisons are meaningless on this host — decode claims need distributions (which reinforces the interleaved-A/B rule programme-wide).

### C15 — Long-prompt prefill acceleration

**Priority:** P1 after C12 diagnosis · **Status:** Phase 1 A/B verdict FAIL (2026-11-13) — kernel kept env-gated off; GEMM-shaped score re-shape recorded as the follow-up candidate

**Goal:** Reduce long-prompt processing time without harming decode or recurrent-state correctness.

Investigation order:

1. Use C12 timings to separate tokenisation, embedding, attention, DeltaNet/recurrent work, MoE, dense projections and output-head costs.
2. Identify compute, bandwidth, expert loading, scheduling or chunk-size bottlenecks.
3. Evaluate prompt chunk sizing and batching. Larger chunks are not automatically better; recurrent state and memory footprint constrain useful sizes.
4. Inspect ARM fused-row kernels for prompt batches, not just single-token decode.
5. Evaluate Metal only where shapes amortise transfer/dispatch overhead. The sparse MoE Metal path previously lost to CPU in recorded tests; do not generalise this to dense layers or every prompt shape.
6. Re-run correctness/parity tests after recurrent-layer batching or state changes.

**Scoping (2026-11-13, from the C12 profile + code reading):**

- Where the cost lives: Qwen3.6-35B-A3B has 40 layers but only 10 full-attention layers (`layer_types`, every 4th; the rest are gated linear attention). The pilot's per-token attention (21.5 → 57.9 → 130.5 ms across 12K/32K/64K, ≈71% of recorded components at 64K) therefore concentrates in those 10 layers, while MoE and linear-attention scale near-linearly.
- Why it is slow (traffic model): `attention()` (qwen36.c ~5318) loops `(head, prompt-row)` over the whole context, calling `q36_kv_dot`/`q36_kv_axpy` per position — each K/V row is re-read by every sharing q-head × every prompt row. With q_heads=16, kv_heads=2 (q_per_kv=8), head_dim=256, fp16 K/V (512 B/row): a 12K-token prefill issues ≈ 16·S·T·512 B ≈ 1.24 TB of K reads **per attention layer**, ≈ 12 TB over 10 layers. The observed 263 s attention timer at 12K implies ≈ 47 GB/s effective — the loop is bandwidth-bound streaming K/V from RAM, not compute-bound.
- **Phase 1 (primary candidate) — row-blocked prefill attention:** process RB prompt rows per head per pass over K/V (the K-row load then feeds RB query rows, like `matmul_q_batch`'s two-row tiling). RB=8 cuts K and V traffic ~8× (each K row read S times instead of 8·S). Bit-exactness is achievable and required: each score is still the same `kv16_dot_lanes(q, K_t)` pair, softmax stays per-row in ascending-t order, and each row's context accumulation stays ascending-t — only the *order of independent pairs* changes, so outputs must remain sha-identical to the unblocked path. Guard: the S=1 decode path keeps the existing loop (no regression surface); blocking applies only when S ≥ RB. Sweep RB ∈ {4, 8, 16} on 4K/12K colds.
- **Phase 2 (secondary) — chunked prefill:** the serve path currently forwards a whole prompt in one step (the pilot recorded one chunk per request). `COLI_PREFILL_CHUNK` semantics exist in colibri.c with a byte-identical-greedy-output verification precedent; porting them bounds prompt-sized activation buffers and adds mux yield points, but does not change the quadratic score work — a scheduling/memory lever, not the attention fix.
- **Phase 0 (measurement, before any code change):** restart with `COLI_TIMERS=1`, run 1K/4K/12K colds once each, record the prefill phase accumulators (`dn/attn/moe/head` ms) and `prefill_chunk_count`. Purpose: within-run per-phase shares at today's machine state, and the unblocked attention baseline the phase-1 A/B compares against. Single observations are fine for shares; the phase-1 decision needs the interleaved A/B rule (drift finding) — blocked vs unblocked alternating on the same process.
- **Phase 0 result (2026-11-13, unblocked kernel, `phaseC15_p0_results.jsonl`):** per-phase prefill accumulators on one cold per size (whole-prompt single forward confirmed: `prefill_chunk_count = 1` at 1K/4K/12K). Per-token attention 2.03 / 5.54 / 16.11 ms at 1K/4K/12K — ×8 tokens gives ×7.9 cost, exactly quadratic. **At 12K the recorded shares are MoE 320.5 s (52%), attention 198.7 s (33%), deltanet 89.5 s (15%)** — attention dominates only from ~32K up (the pilot's 71% at 64K); at agent-relevant sizes MoE's linear ~26 ms/token is the larger absolute component, which keeps C14's expert data movement on the table alongside C15. Attention row-blocking still wins at 12K (a ~8× cut of the 199 s component) and compounds at longer context.
- **Drift, sharpened:** the same 12K cold config measured 778.8 s in the morning memory run and 610.9 s in phase 0 hours later (−22%, no config change). Candidate mechanism: the morning run carried a ~10.1 GB resident peak (memory pressure, weight-page trimming) that the settled evening state (~7.2 GB) does not. Cross-run comparisons remain uninterpretable; interleaved A/B stays mandatory.
- **Decision rule:** adopt row-blocking if the 12K attention timer drops ≥ 20% with sha-identical outputs and no decode-rate regression (the fixture suite plus a real-model cold-reference comparison are the correctness gates); then re-run the C13 matrix colds so the recorded baselines refer to the adopted kernel. If the traffic model is wrong (compute-bound in practice), the timers will show it before any kernel work is written.
- **Phase 1 implemented (commit `57f78c52`):** row-blocked prompt attention behind `Q36_ATTN_ROWBLOCK` (rows per block, 2–64, **off by default**). Decode (S==1), mux rows, ring/window layers and sink heads keep the original loop. Fixture suites pass with the env set: the 16-test prefix-serve contract (+8 subtests) and the 3082-test python suite minus 4 failures that reproduce identically without the env (pre-existing: `test_convert_guard` registry drift, `test_makefile_deps` lint, 2× `test_qwen36_text_stops` flaky `first_emit_after_prefill_s` echo; also `make test-c` is broken at `test_qwen36_tier_int8_engine.c` — a stale 2-arg `slot_ensure_allocated` call, pre-existing).
- **Phase 1 real-model A/B — pending, resumable:** driver `c15_ab.py` + launcher `c15_ab_launch.sh` (both in `researchLogs/logs/colibri-c12-workloads/`), ~1 h end to end. The launcher alternates **one binary** (the committed build) with `Q36_ATTN_ROWBLOCK=0` (byte-identical baseline path) and `=8` across fresh restarts, servers with `COLI_PROMPT_CACHE=0` so the same tagged prompts full-prefill on both configs — the 12 output shas must all match (bit-exactness gate on real weights), plus `prefill_attention_s` deltas against the ≥20% rule and decode rates for no-regression. One partial baseline row exists from the aborted first attempt: `phaseC15_ab_base_r1_partial.jsonl` (4K cold: prefill 139.9 s, attention 19.9 s = 14%, decode 11.1 tok/s). Resumption is one command: `bash c15_ab_launch.sh` (results tee over the per-run files; the server is left DOWN when the session ends).
- **Phase 1 A/B verdict — FAIL (2026-11-13, `phaseC15_ab_{base,blk}_r{1,2}.jsonl`), the kernel stays env-gated OFF.** Correctness held: all 12 output shas match across configs (4K `fb965acd73e5` ×8, 12K `44dc6b752fd6` ×4) — the blocked kernel is bit-exact on real weights, as constructed. But the attention timer got *slower*, not faster: paired deltas 4K −3.8/−7.3/−6.8/−23.4%, 12K −0.2% (r1) and −14.8% (r2), mean ≈ −7.5%; decode rates unchanged (4K ~9–11 tok/s, 12K ~7.8–8.9, within drift in both configs). The ≥20%-reduction decision rule fails outright. **Why the traffic model was wrong:** the 8·S K/V re-reads the old loop makes are absorbed by the cache hierarchy, not RAM — at 12K a layer's K (or V) is 12,320 × 512 B ≈ 6.3 MB per KV head, which sits in Apple Silicon's L2/SLC for the whole pass, so the extra reads cost L2 bandwidth (fast, already near-fully reused within each (head, row) sweep) while the blocked path *adds* strided scratch traffic (`sc` writes at `i·kv_cap` stride across an rbn×kv_cap window plus its read-back). The phase-0 implied "~47 GB/s" was never a DRAM streaming rate. Conclusion: prefill attention is quadratic but **compute/latency-bound per scalar `q36_kv_dot`** (fp16→f32 widening, serial dependent accumulation, non-BLAS codegen), not DRAM-bound — so row-blocking cannot pay, and the lever that remains is re-shaping the score loop as batched GEMM (Accelerate/vDSP or Metal), which changes summation order and forfeits trivial bit-exactness (a different, larger experiment — record as the C15 follow-up candidate, do not start without re-scoping). The negative result is kept in-tree behind the default-off env as the documented A/B evidence; `c15_ab_summary.py` recomputes the verdict from the result files.

**Follow-up re-scope (2026-11-14, post-C18-adoption; no code written):** with the decode-once kernel adopted, MoE at 12K dropped ~44%, and attention is now the **largest single prefill component** (C18 A/B rows: attention 234–274 s of a 588–801 s 12K prefill, ≈ 40–45%; 21–35 s at 4K). The re-shape candidate, sized:

- **The work:** the score pass is, per full-attention layer and KV head, the matrix product `scores[S×T] = Q_rows[S×256] · K^T[256×T]` (fp32 Q rows, fp16 cache K widened), and the context pass is `ctx[S×256] = probs[S×T] · V[T×256]` — two GEMMs per (layer, KV head), the same shapes the x86 r16/tile16 kernels already prove profitable on the MoE side. At 12K that is ≈ 6.2 TFLOP of scores (10 layers × 16 q-heads × ~76 M pairs × 512 flops) plus a V pass of the same order; the measured ~250 s attention timer puts the current scalar loop at ≈ **24 GFLOPS aggregate**, while Accelerate `cblas_sgemm` on the M4's P cores sustains an order of magnitude more. A sgemm-based pass at even a conservative 120 GFLOPS would price the whole score+context work at ≈ 50–60 s (vs ~250 s) plus the K/V widening cost (each layer's K and V converted fp16→fp32 once per pass: 2 × 12,320 × 256 × 2 heads × 4 B ≈ 25 MB/layer, amortised over the 8 q-heads that share each KV head and all S rows).
- **Correctness contract changes — this is the decision the user must sign off on:** scores accumulated by BLAS (FMA/AMX tiling) differ from the scalar loop's order, so logits shift in low bits. Temperature-0 outputs are *usually* unchanged but are **not guaranteed sha-identical**; the engine's current product contract (bit-exact outputs vs the reference decode order, enforced by every A/B sha gate) would be replaced by "deterministic per build, score-level maxdiff measured and bounded". The correctness gate becomes a two-level protocol: (1) fixture: assert per-prompt-token logit maxdiff against the scalar path below a measured tolerance (expected ≲ 1e-3 relative on fp16-grid K/V); (2) real-model: same tagged prompts base vs GEMM — record sha agreement rate and the timer deltas, with agreement required on a defined agent-session prompt set (TBD) rather than everywhere. **Precedent inside this codebase — for more details refer [`docs/METAL-M5MAX-PERF-REPORT.md`](docs/METAL-M5MAX-PERF-REPORT.md) (caveats section):** the Metal backend's parallel expert reductions (PIPE workers / GPU threadgroup reductions) already exhibit exactly this property — run-to-run non-determinism from floating-point non-associativity occasionally flipping an argmax at a token boundary, with output quality and throughput unaffected and the "token-exact" claim explicitly scoped to a deterministic/serial validation config. That report is the working precedent that a bounded-tolerance contract is honest and operational.

**Metal lessons carried forward (2026-11-14, from the prior backend reports — for more details refer [`docs/METAL-M5MAX-PERF-REPORT.md`](docs/METAL-M5MAX-PERF-REPORT.md) and [`docs/METAL-M1ULTRA-FMT2-REPORT.md`](docs/METAL-M1ULTRA-FMT2-REPORT.md); both are GLM-5.2 744B decode reports on other hardware, so treat as constraints, not predictions):**

4. **Kernel-authoring constraints for any new Metal kernel are already catalogued** in [`docs/metal_implementation.md`](docs/metal_implementation.md) (SIMD groups ≠ warps, threadgroup 32–256 only, unified-memory zero-copy, `alignas(16)` param structs — misalignment yields wrong values, not crashes).

### C17 — 27B dense model and C8 Metal investigation

**Priority:** P2 · **Status:** Candidate experiment — **desk assessment recorded (2026-11-16): not proceeding to evaluation on the current evidence**

**Goal:** Use Qwen3.6 27B dense as a controlled workload for dense GEMV, MTP head and Metal-path experiments.

**Desk assessment (2026-11-16, no code, no download): could the evaluation plausibly produce a good surprise on speed and quality, given the colibri stack as it stands? The answer is mostly no — recorded so the decision is arithmetic, not vibes.**

- **Decode on CPU: regression by construction.** Decode is bandwidth-bound and scales with bytes-per-token. The IQ2_XXS 35B-A3B streams only its active slice per token (40 layers × 8 experts × 1.17 MB ≈ 375 MB of expert bytes plus shared weights — order 1.3 GB/token) and measures 13.6 tok/s (1K cell mean, 2 rounds). A 27B dense model touches *all* its weights every token: at IQ2-class ~2 bpw that is order 9+ GB/token — roughly 6–7× the bytes — predicting ~2 tok/s at equal bandwidth; a Q4 dense container is worse still. (Order-of-magnitude desk arithmetic, flagged as such — but the direction is not in doubt: dense trades compute for bytes per token, and decode pays bytes.)
- **Cold prefill on CPU: likely 2–3× slower, not faster.** Dense 27B does ~9× the per-token FLOPs of the A3B's active slice; even at the much higher GEMM efficiency of Accelerate sgemm (>1 TFLOPS at the C15 gate vs the MoE kernel's ~0.21–0.27 TFLOPS post-decode-once), net cold-prefill cost lands ~2–3× above the current 302 s 12K reference. Real agent sessions (93–100% prefix reuse, restores at 0.2–0.5 s TTFT) are insulated, but every new conversation pays it.
- **Quality: a plausible but unproven gain.** 27B dense at comparable quant plausibly edges 3B-active MoE — but C16 just demonstrated that a 3-question probe cannot establish a quality claim, and a real eval set is a project in itself.
- **The two genuine surprise levers both have documented history against them.** (1) Metal GPU serving of dense weights — C8's kernel-level win did not convert to an end-to-end gain, which is why this section's acceptance demands a repeatable request-latency improvement. (2) MTP speculative decode on a bandwidth-bound dense model (verify-k-tokens ≈ one forward could multiply effective decode) — real, but the MoE model already serves with MTP working, and the dense model's own MTP-head quality is unknown; spec decode is a separate lever that does not require switching models.

**Conclusion: the desk arithmetic predicts a decode regression large enough that only the Metal or spec-decode levers could flip the verdict, and both carry inconclusive/negative precedent in this repo. C17 stays parked as a candidate; revisit triggers are a user-prioritised quality goal backed by a real eval set, or a decision to pursue GPU serving as a goal in itself.**

1. Re-establish clean CPU and Metal baselines after C12 instrumentation.
2. Measure prefill and decode separately.
3. Inspect which dense operations dispatch to Metal and which remain on CPU.
4. Revisit C8 IQ2 Metal GEMV for the dense MTP head, measuring dispatch overhead, transfer cost and row shape.
5. Measure MTP on/off with identical prompts and sampling. Acceptance rate alone does not prove benefit.
6. Compare with 35B MoE without conflating architecture, quantisation or workload.

**Acceptance:** proceed with C8 or related Metal work only if the dense workload has a repeatable end-to-end gain. A kernel-level win without request-latency improvement is insufficient.

### C18 — ARM expert-matmul kernel profile (the fused IQ2/IQ3 grid dot)

**Priority:** P1 · **Status:** Phase 2 A/B verdict PASS (2026-11-14) — decode-once adopted as the default (sha-identical outputs, MoE −33…−49%); microbenchmark phase 1 complete

**Goal:** Profile the ARM fused `gq_dot_arm_iq2_xxs` / `gq_dot_arm_iq3_xxs` inner loop — measured in C14 phase 0 as 92% of a 12K prefill's MoE time at only ~77–93 GFLOPS over 6 threads — and decide whether a kernel rewrite is worth its correctness story.

**Where it runs:** on Apple silicon, the CPU-GGUF expert prefill path (`moe_gq_run` → `gq_matmul2_act`/`gq_matmul` → `gq_matmul_act`) falls through to the final dispatch (`schedule(static)` over output rows → `gq_row_all` → fused grid dot): the x86-only `GQ_R16_ON`/tile16/f8 unpack-once kernels ("unpack 16 file rows once") do not compile here, so **the ARM path re-decodes each weight row once per activation row** (`for s { for blk { grid-decode; dot } }` — `GQ_DOT_GRID_ARM`, ggml_quants.h ~1876). Per sub-block of 32 elements the decode costs ~4 grid-table loads + 4 sign-table loads + 4 lane multiplies — comparable instruction count to the dot itself.

**Phase 1 microbenchmark (`researchLogs/logs/colibri-c12-workloads/c16_kernel_bench.c`, results in-session; shapes = the model's: gate/up IQ2_XXS I=2048 O=512, down IQ3_XXS I=512 O=2048; S sweeps C14's measured per-expert row counts):**

- Cells: `matmul` = the engine's exact entry point (`gq_matmul`, OMP per env); `rowall` = per-row dispatch without quantize (single-thread); `decode` = the kernel's weight work with the dot removed; `pre_dot` = the kernel's exact float steps with decode hoisted out of the row loop (bit-exactness verified: `precheck_maxdiff = 0.0` against `gq_row_all`); `pre_dot_omp` = the same under the engine's dispatch shape.
- **Per-thread rates are flat in S** (1 → 455 rows): the fused kernel runs **36 GFLOPS/thread (gate/up IQ2_XXS)** and **24 (down IQ3_XXS)** — decode is 40% / 27% of kernel time and is paid per activation row.
- **The decode-once variant is bit-identical and much faster:** per-thread 52 / 76–79 GFLOPS → 1.44× (IQ2) and 3.2× (IQ3) headroom per thread. For IQ3 the win is mostly that the interleaved decode stalls the dot pipeline; a clean `vdotq` loop on pre-decoded int8 runs at ~78 GFLOPS/thread vs the fused kernel's 24.
- **The fused kernel has a ~115 GFLOPS aggregate cap regardless of thread count** (4/5/6 threads all land at 113–116; 2 threads scale 2×): the gather-heavy decode saturates a shared resource (load ports / L2-SLC), not the cores. The decode-once variant blows past it: **208 GFLOPS (gate/up) and 273 (down) aggregate at 6 threads** under the engine's dispatch shape.
- **Net verdict: a decode-once ARM kernel is worth ~2.2× on expert-matmul aggregate** (flops-weighted mix of the two shapes: ~102 → ~226 GFLOPS), with the float steps unchanged (the microbenchmark's hoisted loop reproduces the fused kernel's bits exactly — same `p·scale` FMA order).
- Quantization (`gq_act_set`) is negligible (≤2% even at S=455); the OMP region overhead per expert is small.
- **Projected end-to-end (arithmetic on C14's measured shares, not yet an engine A/B):** matmul is 92% of MoE (322.6 s of 349.7 s at 12K). At 2.2×, matmul → ~147 s, MoE → ~174 s, 12K prefill ~692 → ~517 s (**≈ −25% TTFT at 12K**); MoE ms/token at 1K similarly ~24 → ~12, 1K prefill ~33 → ~21 s. Attention and deltanet unchanged.
- **Engine-vs-bench gap noted:** the engine's in-situ matmul rate (~93 GFLOPS aggregate at 1K, 77–93 at 12K) is slightly below the bench's fused-kernel rate (~102–116) — expert variety (each expert's weights cold in cache), X gathers, silu, out-accumulation and per-expert OMP churn explain the remainder. The 2.2× headroom claim rests on the *paired* bench cells (same data, same shape, only decode placement differs), not on the absolute levels.

**Phase 2 implemented (commit `af017361`):** decode-once ARM grid dots behind `Q36_EXPERT_DEC1` (off by default) in `ggml_quants.h`'s `gq_row_all`: when the env is `1`, S > 1, and the grid-type gate holds, each weight row is decoded once into int8 + per-32 scales (stack scratch, `I ≤ 16384`), then the fused kernel's exact float steps run against every activation row; `S == 1` decode keeps the fused kernel. Cross-checks so far: the bench binary rebuilt against the modified header shows the engine's own `gq_matmul` entry point at 188.5 / 258.3 GFLOPS aggregate (gate/up, down) with the env on vs 111.8 / 85.3 off; fixture suite 16 passed (+8 subtests) with the env on; full python suite 2702 passed / 4 failed — the same 4 pre-existing failures that reproduce without the env (`test_convert_guard`, `test_makefile_deps`, 2× flaky `test_qwen36_text_stops`).
**Phase 2 real-model A/B — verdict PASS, adopted (2026-11-14, `phaseC18_ab_{base,dec1}_r{1,2}.jsonl`, verdict `phaseC18_ab_verdict.txt`).** One committed binary, interleaved base/dec1 × 2 rounds across fresh restarts, `COLI_PROMPT_CACHE=0`. Gates: (1) **sha gate PASS** — all 12 output shas identical across configs (4K `a8aaa8ef0bf0` ×8, 12K `8cf3e944e430` ×4) — bit-exact on real weights, as constructed. (2) **MoE rule PASS decisively** — paired `prefill_moe_s` deltas +32.7% to +48.8% (4K means +40.6%/+45.7%, 12K mean +44.1%), far beyond the ≥20% rule. (3) **decode no-regression PASS within drift** — decode is code-identical (S==1 keeps the fused kernel), and the paired deltas (4K −7.0/−5.9/−0.8/+1.2%, 12K −8.9/−6.3%) sit inside the ambient drift band established by the unchanged attention/deltanet timers (r1 12K attention drifted +13% and deltanet +15% with identical code; dec1 runs came second in each round while the machine degraded monotonically — base r1→r2 alone went 681→801 s at 12K). End-to-end TTFT: 4K −9.7/−25.1/−32.0/−32.0%, 12K −13.7/−24.0% (mean −19.3%). **Default flipped ON (commit `af017361` + default flip): `Q36_EXPERT_DEC1=0` restores the fused grid kernel**; the S==1 decode path and non-grid types are untouched either way. Over the run the resident set decays 10.1 → 7.2 GB (macOS trimming file-backed weight pages under pressure); peak, not instantaneous RSS, is the honest number. Whole-stack peak ≈ 10.3 GB: headroom exists on this host, but a concurrent second client competes for the remainder.
- **Same-run timing (quiet machine, fresh restart):** cold prefills 32.5 / 184.8 / 778.8 s at 1K/4K/12K (31.9 / 45.1 / 63.2 ms/token); restores 0.100 / 0.313 / 0.574 s TTFT (n=2 each, outputs exact vs their cold; per-token restore cost declines 0.095 → 0.070 → 0.042 ms/token — a fixed ~60–80 ms plus a ~37 µs/token slope, vs the matrix's uniform ~34 µs/token). Sustained decode on restored state: 16.2 / 10.5 / 8.6 tok/s; on cold state: 14.0 / 9.3 / 7.2 tok/s — restored state decodes ~10–15% faster at every size.
- **Drift again, bounded:** this pass's ≥4K rows are uniformly slower than yesterday's matrix (4K cold 184.8 vs 158.5 s p50; 12K cold 778.8 vs 677.1; 4K restore 0.31 vs 0.19; 12K restore 0.57 vs 0.42) while the 1K rows match yesterday almost exactly (32.5 vs 33.0 cold; 0.100 vs 0.102 restore). No config changed. Cross-day comparisons stay uninterpretable for the larger sizes; the interleaved A/B rule stands, and 1K-class measurements appear drift-stable across days.
- **Retention exercised by a third-party workload, with observability:** between sessions, the user's `brewer` client stored its own conversation snapshots, which displaced all of yesterday's matrix snapshots (oldest-first under the 8 GB byte budget) — the reason the first attempt's untagged restores had to full-prefill; the self-contained tagged-cell design fixes that class of surprise. - Conclusion for C15 scoping: memory is not the binding constraint for long-prompt prefill on this host — peak RSS is flat in prompt size once weights are resident, while prefill time is superlinear (32 → 63 ms/token over 1K → 12K). The attention-prefill experiment remains the right target.

## 8. Explicit non-goals

- Do not chase decode tok/s at the expense of agent TTFT without measuring the trade-off.
- Do not assume MTP should be enabled by default; current 35B measurements show it can lose after C11.
- Do not reserve or lock the full user-offered 5 GB blindly.
- Do not build a second prefix cache before measuring `kv_prefix.h`.
- Do not implement Q4_K_M-specific kernels before profiling the exact model.
- Do not assume Metal is automatically faster than the M4 CPU for sparse MoE.
- Do not accept a benchmark improvement without correctness and repeatability.
